# Технічний план Lamari

## 1. Мета й межі MVP

MVP має дозволити покупцю переглядати каталог прикрас, фільтрувати товари,
обирати варіант, додавати його в кошик, оформлювати й оплачувати замовлення та
відстежувати статус. Менеджер керує каталогом, залишками, замовленнями,
промокодами, контентом і базовою аналітикою в окремій захищеній адмінпанелі.

До першого релізу не включаємо складну ERP/CRM, мультивалютний облік,
маркетплейс із кількома продавцями, мобільний застосунок і програму лояльності.

## 2. Рекомендований стек

- Backend: PHP 8.3+, Laravel 13, REST/webhook endpoints, черги та scheduler.
- Storefront: Inertia.js, Vue 3, TypeScript, Tailwind CSS, Vite; SSR для SEO.
- Адмінпанель: Filament 5 на окремому `/admin` з окремим guard/ролями і 2FA.
- Дані: PostgreSQL 17; Redis для кешу, сесій, rate limits і черг.
- Пошук у MVP: PostgreSQL full-text/trigram; Meilisearch лише після вимірювання.
- Файли: S3-сумісне приватне object storage, WebP/AVIF derivatives.
- Тести: Pest, Laravel HTTP/feature tests, Playwright для критичного checkout.
- Інфраструктура: Docker Compose локально; окремий staging; CI/CD із ручним
  production gate.

Це модульний моноліт: він дешевший і простіший в експлуатації за мікросервіси,
але домени `Catalog`, `Cart`, `Checkout`, `Orders`, `Payments`, `Shipping`,
`Promotions`, `Content` відділяються сервісами й подіями.

## 3. Функціональні модулі

### Вітрина

- Головна, колекції, категорії, каталог, пошук і фільтри.
- Картка товару: галерея, матеріал, покриття, розміри, догляд, наявність.
- Варіанти товару та SKU; супутні й нещодавно переглянуті товари.
- Кошик для гостя/користувача, промокод, checkout без обов'язкової реєстрації.
- Кабінет: профіль, адреси, історія та статус замовлень.
- Українська мова й UAH у MVP; структура готова до локалізації.

### Адмінпанель

- CRUD категорій, колекцій, товарів, варіантів, медіа та характеристик.
- Облік доступного/зарезервованого залишку й журнал рухів.
- Замовлення, оплати, повернення, доставки, внутрішні нотатки.
- Знижки/промокоди з періодом дії, лімітами та правилами застосування.
- CMS-блоки головної, статичні сторінки, SEO metadata і redirects.
- Ролі: `owner`, `manager`, `content_manager`, `support`; журнал дій.

## 4. Нефункціональні вимоги

- Mobile-first, WCAG 2.2 AA для ключових сценаріїв.
- Core Web Vitals: LCP до 2.5 с, INP до 200 мс, CLS до 0.1 на staging audit.
- SEO: SSR, canonical, sitemap, robots, Open Graph, Product/Offer JSON-LD.
- Безпека: CSRF, CSP, rate limiting, secure cookies, 2FA для адмінів,
  перевірка підпису webhook, idempotency keys, секрети поза репозиторієм.
- Privacy by design: згода на необов'язкову аналітику, мінімізація PII,
  політики зберігання/видалення, журнал адміністративних дій.
- Надійність: щоденні backup БД, versioning файлів, health checks, error tracking.

## 5. Етапи реалізації

1. Підтвердження вимог: асортимент, варіанти, доставка, оплата, дизайн-напрям.
2. Scaffold Laravel, CI, Docker, staging secrets і базова дизайн-система.
3. Каталог, медіа, залишки й адмінпанель.
4. Storefront, пошук, фільтри, кошик і SEO.
5. Checkout, платежі, доставка, email/SMS та webhook reconciliation.
6. Кабінет, промокоди, CMS, аналітика й юридичні сторінки.
7. Автотести, security/performance/accessibility audit, контентне наповнення.
8. Тестове розгортання: окремий host, `noindex`, Basic Auth/VPN, sandbox APIs.
9. Приймання власником і виправлення. Production — лише після окремого дозволу.

## 6. Definition of Done для staging

- Повний сценарій від каталогу до тестової оплати проходить на мобільному й ПК.
- Webhook-и повторювані та не створюють дубль оплати/замовлення.
- Залишки резервуються атомарно й повертаються після timeout/скасування.
- Немає критичних/високих вразливостей; backup і restore перевірені.
- Адмінпанель недоступна без 2FA; права ролей покриті тестами.
- Staging не індексується й не використовує production credentials.
